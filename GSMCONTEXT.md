# 1. PROJECT OVERVIEW

## 1.1 Monorepo Structure

The repo is a Yarn workspaces monorepo with three packages as defined in [package.json](package.json):

- [packages/client](packages/client) - React 19 + Vite frontend.
- [packages/server](packages/server) - Apollo GraphQL + Express backend with TypeORM.
- [packages/types](packages/types) - Shared TypeScript types generated from the GraphQL schema.

The workspace configuration is minimal and points to `packages/*` only.

## 1.3 Dependency Injection (Inversify)

The backend uses an Inversify container in [packages/server/src/inversify/container.ts](packages/server/src/inversify/container.ts).

- All repositories and services are bound with singleton scope.
- `AppDataSource` is bound as `TYPES.DbContext` and injected into repositories.
- Domain services (Tag, Vendor, Tender, etc.) are all resolved via container per resolver.

Example bindings include:

```ts
container.bind<ITagRepository>(TYPES.ITagRepository).to(TagRepository);
container.bind<ITagService>(TYPES.ITagService).to(TagService);
```

# 8. IDENTIFIED GAPS FOR TENDER WORKFLOW

Based on current code, these workflow gaps are present:

1. **Missing status/state engine (backend).**
   - Backend tender entity only has `name` with no status, dates, or phase fields.
   - No workflow rules are enforced in backend services.

2. **Missing controlled transitions.**
   - Frontend uses `draft` / `published` / `closed` in local state only.
   - Backend does not validate or persist status transitions.

3. **Missing UI gating.**
   - Frontend does not lock UI fields based on permissions or status beyond a simple `closed` check.
   - No role/permission-based gating in UI routes or components.

4. **Missing backend validation rules.**
   - There are no backend checks for publish requirements, date ranges, or vendor eligibility criteria.

5. **Missing mail lifecycle control.**
   - VendorTag has `enableMail`, but no mutation exists to change it.
   - Tender-related email notifications are not implemented.

6. **Mismatch between frontend and backend models.**
   - Frontend expects a rich tender model.
   - Backend stores only `name` and metadata.

# 9. RECOMMENDED ARCHITECTURE FOR TENDER WORKFLOW

This proposal fits the current architecture (TypeORM + GraphQL + Inversify) and uses existing module patterns.

## 9.1 TenderStatus Enum

Introduce a `TenderStatus` enum in the backend and align with frontend values.

Recommended statuses:

- `DRAFT`
- `PUBLISHED`
- `CLOSED`
- `CANCELLED` (optional)

## 9.2 State Transition Rules

Add explicit transition rules to `TenderService`:

- `DRAFT -> PUBLISHED` (requires required fields)
- `PUBLISHED -> CLOSED`
- `PUBLISHED -> CANCELLED`
- Prevent any changes after `CLOSED` except archival fields

## 9.3 Required DB Changes

Extend Tender entity in [packages/server/src/entities/Tender.ts](packages/server/src/entities/Tender.ts):

- `referenceNumber: string`
- `issuingDepartment: string`
- `tenderType: enum`
- `description: text`
- `estimatedValue: number`
- `categories: string[]` (or join table)
- `status: TenderStatus`
- Date fields (publish/submission/closing)
- `minimumExperience`
- `mandatoryDocuments: string[]`
- `allowedVendorTypes: string[]`

If arrays are used, ensure DB compatibility (`text[]` in PostgreSQL).

## 9.4 Required GraphQL Changes

Update `Tender` type and inputs in [packages/server/src/components/tender/schema.ts](packages/server/src/components/tender/schema.ts):

- Add all fields defined above
- Add `status` enum
- Add mutations for `publishTender`, `closeTender`

## 9.5 Required UI Restructuring

- Replace mock `tenders.service.ts` with Apollo GraphQL queries/mutations.
- Normalize the form flow so that the backend is the source of truth.
- Integrate `Tag` and `TenderTag` using actual GraphQL operations.

## 9.6 Tagging Integration

### Backend

- Add a `TenderTag` GraphQL module (schema + resolver + service + repository).
- Create mutations:
  - `addTagToTender(tenderId, tagId)`
